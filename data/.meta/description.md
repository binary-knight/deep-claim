# data

**Purpose:** The shipped game content of Deep Claim: seven flat JSON files holding the resource, tech, region and event definitions, the balance and built-in-competitor tuning numbers, and every sentence the player reads. `content::loadFromDirectory` (`content/src/loader.cpp`) parses and validates all seven into one `sim::Content` (`sim/include/sim/content.h`); the directory contains no code.

## Key Components
- `resources.json` — top-level array of resource records (4 entries). Fields: `id`, `name`, `base_price`, `base_demand_tonnes_per_day`, `base_output_tonnes_per_day`, `elasticity`, `volatility`, `storage_cost_per_tonne_month`, `unlocked_by` (tech id or `null`). Parsed by `parseResources` into `Content::resources` (`sim::ResourceDef`); `unlocked_by` is linked later by `resolveUnlocks`.
- `techs.json` — top-level array of tech records (10 entries). Fields: `id`, `cost`, `duration_days`, `requires` (array of tech ids, optional), `effects` (array of `{type, value}` or `{type, resource}`). Effect types: `survey_noise_mult`, `extraction_capex_mult`, `opex_mult`, `output_mult`, `storage_cost_mult` (take `value`), `unlock_resource` (takes `resource`). Parsed by `parseTechs` / `parseTechEffect` into `Content::techs` (`sim::TechDef`), then `checkTechCycles`. No name or description here; those come from `strings.json`.
- `regions.json` — top-level array of region records (3 entries). Fields: `id`, `name`, `plot_count`, `land_price` `{min, max}`, `plot_area_hectares` `{min, max}`, `deposits` (object keyed by resource id, each `{presence_prob, tonnes_median, tonnes_spread, tonnes_max_mult}`). Parsed by `parseRegions` / `parseRange` / `parseDeposits` into `Content::regions` (`sim::RegionDef`, `sim::DepositPrior`).
- `events.json` — top-level array of world-event records (4 entries). Fields: `id`, `daily_weight`, `min_year` (optional, default 1), `duration_days`, `effects` (array of `{type, value}` plus `resource` for `demand_mult`). Effect types: `demand_mult`, `opex_mult`, `land_price_mult`. Parsed by `parseEvents` / `parseEventEffect` into `Content::events` (`sim::EventDef`). No name or description here; those come from `strings.json`.
- `balance.json` — one top-level object with 32 keys: 30 scalar knobs (starting capital, loan terms and limits, survey cost/duration/noise, mine capex/build/opex/mothball, auction window, plot listing cadence, opening-hand rules, relist and bankruptcy limits, market smoothing, demand and price clamps, demand growth), the nested object `default_sell_policy` `{enabled, reserve_tonnes, floor_price}`, and the boolean `default_cover_costs`. Parsed by `parseBalance` into `Content::balance` (`sim::BalanceParams`).
- `ai.json` — one top-level object with 19 scalar keys tuning the built-in competitor (sell thresholds, plot valuation haircuts and required returns, first-mine variants, supply discount, payback horizon, bid premiums, prospect limit, mine reopen/idle rules, cash reserve, research and loan floors, loan sizes). Parsed by `parseAi` into `Content::ai` (`sim::AiParams`).
- `strings.json` — the prose catalogue (spec 002): one flat top-level object of `key: template` strings, 303 entries, keys sorted, one per line. Key prefixes: `ui.` (176), `notice.` (39), `reject.` (30), `status.` (30), `tech.<id>.name|description` (20), `event.<id>.name|description` (8). Templates use `{placeholder}` names; plural variants are sibling keys ending `.one` / `.many` (11 pairs). Parsed by `parseStrings` / `readStringEntry` into `Content::strings`, which also fills `TechDef::name/description` and `EventDef::name/description`.

## Dependencies
- Consumed only through `content/src/loader.cpp` (`dc::content`, nlohmann-json); file names are the constants `kResourcesFile` ... `kStringsFile` in `content/include/content/loader.h`. All seven files must be present: `loadFromDirectory` reports `cannot read <path>` for any missing one.
- Target struct layout is `sim::Content` and its member structs in `sim/include/sim/content.h`; string keys for notices and reject reasons are derived from `sim::noticeKindName` and `sim::rejectReasonName`.
- `strings.json` is generated, not hand-edited: `tools/prose/draft.tsv` (source of truth for meaning) -> `tools/prose/polish.sh` with `tools/prose/voice.md` -> `tools/prose/polished.tsv` -> `tools/prose/to_json.py polished.tsv data/strings.json` (sorted keys, two-space indent, `ensure_ascii=False`, trailing newline). Key scheme is specified in `docs/specs/002-prose-catalogue.md`.
- Cross-file references inside the data: `resources[].unlocked_by` -> tech id; tech `unlock_resource` effect, event `demand_mult` effect and region `deposits` keys -> resource id; `techs[].requires` -> tech id; `strings.json` `tech.*` / `event.*` keys -> tech and event ids.
- Readers of the directory: `deep_claim` (`game/src/main.cpp`), `deep_claim_layout_probe`, `deep_claim_replay` (`game/session/replay_main.cpp`, default for its data path), `sim_runner` (default, overridable with `--data`), and `sim_tests` (`tests/data_files_test.cpp`, `tests/strings_test.cpp`, `tests/test_strings.h`). Each gets the compile definition `DC_DATA_DIR="${CMAKE_SOURCE_DIR}/data"` from its `CMakeLists.txt`.
- Shipping: `game/CMakeLists.txt` defines the always-run custom target `deep_claim_assets`, which `copy_directory`s `data/` to `$<TARGET_FILE_DIR:deep_claim>/data`. At start-up `locate("data", DC_DATA_DIR)` in `game/src/main.cpp` prefers `<SDL_GetBasePath()>/data` and falls back to the source-tree path.

## Patterns
- Data-driven content: plain JSON, one file per `sim::Content` member, entities identified by snake_case string ids and cross-referenced by id (resolved to index-based `ResourceId`/`TechId` at load).
- Array files (`resources`, `techs`, `regions`, `events`) are ordered lists of objects; array order becomes the entity index. Object files (`balance`, `ai`, `strings`) are single flat-ish objects of named knobs or keys.
- Money and fractional values are written as JSON decimals and converted by the loader to `sim::Money` (2 decimal places) and `sim::Fixed` (6 decimal places); day counts and tonnages are integers.
- Load order in `loadFromStrings`: resources, techs (+ cycle check), `resolveUnlocks`, regions, events, balance, ai, then strings last because the per-id `tech.*` / `event.*` keys depend on parsed ids. All errors across all files are collected (`LoadError{file, path, message}`), and `Content` is returned only when there are none.
- Display text is separated from mechanics: tech and event names/descriptions live in `strings.json`, while resource and region `name` stay in their own files.

## Constraints
- Strict schema: every object is checked with `allowKeys`, so an unknown key in any file is a load error; `null` is treated as an absent key. All fields are required except `resources[].unlocked_by`, `techs[].requires` and `events[].min_year`.
- Ids must match `[a-z0-9_]+` and be unique within their file. `resources.json` and `regions.json` must be non-empty.
- Numeric bounds are enforced per field in the loader (for example effect multipliers 0.01 to 100, day counts up to 36000, money magnitude up to 1e11, fixed magnitude up to 1e6, probabilities 0 to 1); values with more decimal places than `Money`/`Fixed` hold are rejected. Range objects require `min <= max`.
- Cross-field rules: `loan_min_principal <= loan_max_principal`, `opening_min_mineable <= plots_listed_at_start`, `mine_capex_per_hectare <= 100000000` (balance); `bid_premium_high >= bid_premium` (ai).
- Reference rules: tech prerequisites must exist, not be self-referential and form no cycle; `unlocked_by` and the tech's `unlock_resource` effect must agree in both directions; value-type tech effects may not carry `resource`, `unlock_resource` may not carry `value`; only `demand_mult` events may carry `resource`; deposit keys must be known resources.
- `strings.json` must contain exactly the expected key set: the 245-entry `kStringKeys` table in the loader, `tech.<id>.name|description` and `event.<id>.name|description` for every loaded tech and event, and `reject.<name>` for every `sim::RejectReason`; missing and unknown keys are both errors. Values must be non-empty strings with well-formed `{name}` placeholders (lower-case letters and underscore only) drawn from the per-key allowed set.
- Save compatibility: `sim::hashContent` (`sim/src/save.cpp`, `sim/include/sim/serialize.h`) hashes resources, techs, regions, events, balance and ai, so any edit to `resources.json`, `techs.json`, `regions.json`, `events.json`, `balance.json` or `ai.json` invalidates existing saves and traces. `Content::strings` is not hashed, so prose and description edits in `strings.json` do not; the exception is the `tech.<id>.name` and `event.<id>.name` values, which are copied into the hashed defs.
- Invariants pinned on the shipped files by `tests/data_files_test.cpp`: 4 resources, 10 techs, 3 regions, 4 events, 120 plots in total; `lithium` unlocked by `lithium_processing`; iron revenue per mine at base equals 4.5 times `mine_opex_per_day` and is the lowest of all resources; every deposit `tonnes_max_mult` is 4; `supply_discount` is 1, first-mine AI terms are no stricter than the ordinary ones, `opening_mineable_presence` is 0.5; `northern_shield` and `copper_belt` classify as mineable at start and `salt_flats` as locked; `plots_listed_at_start >= opening_min_mineable`; opening-hand rules hold for seeds 1 to 200.
- Invariants pinned by `tests/strings_test.cpp`: every notice kind and reject reason renders without leftover `[` or `{`; rejection notices read as one capitalised sentence ending in a single full stop; `tech.lithium_processing.name` is `Lithium Processing`; `tools/prose/draft.tsv` and `strings.json` have the same key set and the same placeholders per key. `tests/test_strings.h` relies on `strings.json` having one key per line.
