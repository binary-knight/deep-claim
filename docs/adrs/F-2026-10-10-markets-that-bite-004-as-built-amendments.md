# ADR-F-2026-10-10-markets-that-bite-004: As-built amendments to records 002 and 003

**Date:** 2026-10-10
**Status:** Accepted
**Context:** This record amends ADR-F-2026-10-10-markets-that-bite-002 and -003. Neither is superseded; everything in them not named here stands. Four statements in two accepted records are not true of the build. Record 002 says the runner calls the margin function each day, and that the golden hash moves because mine state grows. Record 003 says the release sweep runs under a 60-second ceiling with a shorter ungated sweep in the sanitizer preset, and gates on a mine "idled for at least 30 days" without saying what idled means. The architecture review found the records inaccurate, with the corrections held only in `docs/DESIGN.md`. Accepted records are not edited, so this record carries the corrections.
**Decision:**
1. *The runner measures the data's break-even and does not call the margin function (amends 002).* `belowBaseBreakEven` in `sim_runner/main.cpp` asks whether one mine at base output takes less than the ore's cost at the day's price: price times `base_output_tonnes_per_day` below `mine_opex_per_day`, with no research or event multiplier. This is not a second source of truth, because it is not a mine's margin. It is a property of the data, the same for every seed, and the same ratio that `tests/data_files_test.cpp` holds to the chosen share of base price. A gate on the data should measure the data. What any actual mine earns is still worked out only by `sim::mineDailyMargin` and `sim::mineBreakEvenPrice`, which serve the tick and the view; the AI and the client read the view.
2. *The golden hash did not move; a second golden test was added (amends 002).* `kGolden` in `tests/determinism_test.cpp` is still `0x2a5da3177ab7c69d`. Its run gives no orders, so no mine is built and the two new mine fields are hashed in an empty list. "Golden state hash of a played game is stable across platforms" was added beside it: `kGoldenPlayed`, three years of the built-in competitor giving both companies' orders on the in-code fixture, checked again after a save and load.
3. *The 60-second ceiling is a 180-second timeout (amends 003).* The gated sweep took 28 to 62 seconds in a Release build depending on the machine's load. `sim_runner/CMakeLists.txt` runs it in full (50 seeds, 20 years) in Release, RelWithDebInfo and MinSizeRel builds without the sanitizers, judged by exit code, with `TIMEOUT 180` and a failure if any check prints "not evaluated". Every other build, debug included and not only the sanitizer preset, runs 2 seeds (1 under the sanitizers) with a 300-second timeout. That run is judged by its output: every check must be printed, the four checks that judge each seed on its own must pass, and a sanitizer report fails it.
4. *Idled means mothballed 30 days or more and then reopened (amends 003).* A seed counts toward the `idled_mines` gate only when a mine stood mothballed for at least 30 days in a row and then went back to operating within the run. A mine left mothballed, for example because its extractable ore ran out, shows no price decision and does not count. Mine-days idled, a reported figure, still counts every mothballed day.

**Consequences:** The records and the code agree again, and a reader of 002 or 003 must read this record with them. The runner's bite measure cannot drift from the sim's margin rule, because it never used it; it changes only when the data changes. A change to mine state that the bare golden run cannot see now moves `kGoldenPlayed`, which has been recorded on Linux/GCC only and pins the two new fields at zero, since no fixture mine runs at a loss. Debug and sanitizer builds no longer gate the economy: a broken gate fails only an optimized build, and the output expression pins the order of the summary's keys. The idled gate is stricter than the one record 003 describes; it still does not prove that price was the reason a mine was idled, only that the mine came back.
