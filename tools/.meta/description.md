# tools

**Purpose:** Developer-side authoring scripts and their working data, run by hand to regenerate committed assets: UI design-token and icon assets for the game client, and the player-facing prose catalogue. Nothing here is compiled, linked or executed by the CMake build or by CI.

## Key Components
- `design/` - Two Python generators: `tokens_to_rcss.py` (`docs/design/tokens.css` -> `game/assets/ui/tokens.rcss`) and `icons.py` (procedural 7-icon sprite sheet -> `game/assets/ui/icons.tga`).
- `prose/` - The prose pipeline for `data/strings.json`: `draft.tsv` -> `polish.sh` (external `agy` LLM CLI plus `voice.md`) -> `polished.tsv` -> `to_json.py`; also `README.md` and the reference file `agy-raw.tsv`.
- No files are tracked directly in `tools/`; there is no top-level README, `CMakeLists.txt` or shared module.

## Dependencies
- Runtime: Python 3.9 or later (standard library only: `re`, `sys`, `pathlib`, `math`, `struct`, `json`), bash with GNU `grep`/`awk`/`sort`/`tr`, and the external `agy` CLI (network access) for `prose/polish.sh`.
- No Python packaging or lint configuration exists in the repository (no `pyproject.toml`, `requirements.txt`, `setup.py`, `setup.cfg`, ruff/flake8/mypy config).
- Reads from other top-level directories: `docs/` (`docs/design/tokens.css`).
- Writes to other top-level directories: `game/` (`game/assets/ui/tokens.rcss`, `game/assets/ui/icons.tga`) and `data/` (`data/strings.json`).
- Incoming from `tests/`: `tests/design_tokens_test.cpp` checks `game/assets/ui/tokens.rcss` against `docs/design/tokens.css` and asserts the generator's header marker; `tests/strings_test.cpp` reads `tools/prose/draft.tsv` and compares it with `data/strings.json`. Both are sources of the `sim_tests` executable in `tests/CMakeLists.txt` (built when `DC_BUILD_TESTS=ON`, the default) and run under `ctest` in `.github/workflows/ci.yml`, so CI validates the committed outputs without ever running the scripts.
- No C++ code, no vcpkg dependency, no link edge to any CMake target.

## Patterns
- Generate, commit, verify: each script writes a file that is checked in; freshness is checked after the fact by Catch2 tests reading the committed files, not by a build step.
- One directory per concern (`design/`, `prose/`), with no code shared between them.
- Python: single-file CLIs with a docstring usage message and `main(argv) -> int`; output paths are command-line arguments, not hard-coded.
- Shell: one bash script (`prose/polish.sh`) with `set -euo pipefail` and a keep-the-draft fallback.
- Data: headerless two-column TSV (`key<TAB>text`) as the editable source format for prose.
- Markdown: `prose/README.md` documents the prose pipeline; `prose/voice.md` is the style brief fed to the LLM.

## Constraints
- The scripts are run manually with explicit input and output paths; a change to `docs/design/tokens.css` or `tools/prose/draft.tsv` without regenerating the outputs is caught only by the tests above.
- `tools/prose/draft.tsv` is a test input: moving or renaming it breaks `tests/strings_test.cpp`.
- The string `GENERATED by tools/design/tokens_to_rcss.py` is asserted by `tests/design_tokens_test.cpp`, so the script's path is part of a tested contract.
- `prose/polish.sh` is the only component that needs a non-standard program (`agy`) and network access; its output is non-deterministic and is reviewed and committed as `polished.tsv`.
- No automated tests exist for the scripts themselves, and `design/icons.py` output is not covered by any test.
